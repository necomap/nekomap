## 2026-09-30: お問い合わせフォームの通知メールを新規実装（今までメール送信処理自体が存在していなかった）

「問い合わせページからテスト送信したが管理者にも入力した送信元アドレスにもメールとどかない」との報告を受けて調査した結果、**バグではなく、そもそも`/contact`ページにはメールを送る処理が一度も実装されていなかった**ことが判明した。`pages/contact/index.js`の送信処理は`contacts`テーブルへの保存のみを行っており、画面上の「管理者が確認後、メールにてご連絡いたします」という案内文は「管理者が管理画面を手動で見に行って気づいた後、管理者自身のメールソフトで個別に返信する」という意味でしかなく、新着を知らせる自動通知は仕組みとして存在していなかった。

### 実装した内容
- `pages/api/contact/notify.js`を新規作成。`RESEND_API_KEY`が設定されていれば、以下の2通を送信する
  1. 管理者（`role='admin'`の全ユーザー）への通知メール。返信先(reply-to)を送信者本人のメールアドレスにしてあるので、管理者はメールソフトの「返信」でそのまま本人に返信できる
  2. 送信者本人への受付完了メール（入力したメールアドレス宛。送信内容の控えつき）
- `pages/contact/index.js`: `contacts`テーブルへの保存が成功した後、上記APIを呼び出すよう変更。メール送信に失敗しても、お問い合わせ自体は保存済みのため送信完了画面はそのまま表示する（メールはあくまで補助的な通知という位置づけ）
- `contacts`テーブルのSELECTは管理者専用のRLSになっており、フォーム送信者（未ログインの場合が多い）は自分の投稿を読み返せないため、DBに保存し直した内容を読み直すのではなく、クライアントが送信したのと同じ内容をそのままAPIにも渡す設計にした（INSERT自体が誰でも可能な設計と同じ信頼レベルであり、追加の権限チェックは不要と判断）

### 【要確認】RESEND_API_KEYの設定
- ローカルの`.env.local`を確認したところ`RESEND_API_KEY`が設定されていなかった。これが未設定だと、今回実装した通知メールも（既存のチーム招待メール・プッシュ通知に付随するメール通知も）すべて「エラーにはしないが何も送信しない」という扱いになり、静かにスキップされる
- **本番（Vercel）の環境変数に`RESEND_API_KEY`が設定されているか、Vercelのダッシュボード → Settings → Environment Variablesで確認をお願いしたい**（本セッションのツールからはVercelの環境変数を直接確認できなかったため）。あわせて、独自ドメインをResendで認証していない場合は送信元が`onboarding@resend.dev`になり、Resend側の制限で送信先が限定される場合があるので、その場合はResend側の設定も確認してほしい

## 2026-09-30: TNRカレンダーの閲覧を活動者アカウント以上に制限

「TNRカレンダーはユーザーごと？」という質問への回答として、TNRカレンダー（`/tnr`）はユーザーごとの個別カレンダーではなく、ログイン済みなら誰でも同じ内容が見える全員共有の1つのカレンダーであることを確認。その上で「見れるのは活動者以上に制限」との依頼を受け、閲覧のみを制限した。

### 【要Supabase SQL Editorでの実行】閲覧ポリシーの変更
- `DB/add_tnr_visibility_tier.sql`を新規作成。`tnr_schedules`の既存SELECTポリシー（マイグレーション履歴に記録がなく名前が不明だったため、動的にすべて洗い出して削除）を、新ポリシー「活動者以上が閲覧可能」に置き換え
  - 閲覧可能: 活動者アカウント以上（活動者・団体・管理者）、および投稿者本人（自分の予定は引き続き見える）
  - 一般アカウント・未ログインユーザーは、自分が投稿したもの以外は一覧に表示されなくなる
- 投稿（新規追加）・完了フラグの更新は今回変更していない（従来通りログイン済みユーザーなら誰でも可能）
- **このSQLをSupabaseダッシュボードのSQL Editorで実行するまでは、閲覧範囲は変更されない**ので、実行をお願いしたい

### コード側の変更
- `pages/tnr/index.js`: 一覧上部に、閲覧が活動者アカウント以上に制限されていることを説明する文言を追加（一般アカウントのユーザーが見たときに「予定はありません」と誤解しないように）

### ドキュメント更新
- `docs/仕様書.md` §3.8に、全員共有のカレンダーであることと、新しい閲覧制限の内容を追記

## 2026-09-30: スポット（トイレ・フード・猫ハウス）の閲覧範囲を種類ごとに細分化

「トイレは活動者以上、フード・ハウス場所は団体アカウント以上で表示にしたい」との依頼を受け、これまで「フードのみ限定・トイレ/猫ハウスは誰でも閲覧可」という二分法だったcat_spotsの閲覧範囲を、種類ごとの三段階に変更した。あわせて、スポット一覧の説明文から一般ユーザーには関係のない「・管理者」の記載を削除した。

  - フード(food)・猫ハウス(house): 団体アカウント(認証済み)以上のみ閲覧可能に変更（猫ハウスは従来「誰でも閲覧可」だったが、フードと同じ制限に変更。活動者は今回は対象外とし、様子を見ながら将来的に開放する可能性がある旨をSQLファイル内にもコメントで残した）
- **このSQLをSupabaseダッシュボードのSQL Editorで実行するまでは、閲覧範囲は変更されない**ので、実行をお願いしたい

### コード側の変更
- `components/MapView.js`
  - `loadCatSpots()`: 種類ごとの表示可否は上記のRLSポリシー側で制御されるようになったため、クライアント側で行っていた「フードかつ一般アカウントなら非表示にする」という二重チェック（`userType`取得処理ごと）を削除。取得できた行をそのまま表示するだけのシンプルな実装に変更
  - `VisibilityInfo()`（地図右上の「ⓘ 見え方について」パネル）: 「一般・活動者」と「団体・管理者」の二分法だった説明を、一般／活動者／団体の三段階に書き直し、トイレとフード・猫ハウスで扱いが異なることを明記
- `pages/spots/index.js`: 一覧上部の説明文を新しい三段階の閲覧範囲に合わせて書き直し、ご指摘のとおり「・管理者」の記載を削除（管理者はどのアカウント種別の制限も受けないため、この一般向けの説明文に含める意味がなく、混乱のもとだった）

### ドキュメント更新
- `docs/仕様書.md` §3.2の説明文と「アカウント種別による情報公開範囲の違い」表を、トイレ／フード・猫ハウスで別行になるよう更新し、活動者アカウントが一般に対して持つ追加の閲覧権限（トイレ）を明記

### 今後の予定（今回は対応していない）
- フード・猫ハウスについて、活動者アカウントにも公開範囲を広げるかどうかは「様子を見つつ」判断する方針。開放する場合は`DB/add_spot_visibility_tiers.sql`末尾のコメントの通り、SQLの条件に`account_type = 'activist'`を追加するだけでよい（フロント側の変更は不要）

## 2026-09-30: 第三者攻撃対策のセキュリティレビュー（未認証メール送信の踏み台を修正・基本的なセキュリティヘッダーを追加）

「悪意ある第三者からの攻撃対策が必要な箇所があれば対策したい」との依頼を受け、コード全体（API・RLS・XSS対策・シークレットの取り扱い）を見直した。結果、実際に悪用可能な問題が1件見つかり修正、加えて予防的な対策を1件追加した。

### 【重要・修正済み】未認証のメール送信踏み台（`pages/api/org/invite-email.js`）
- 発見: このAPIはログイン確認が一切なく、クライアントから受け取った宛先メールアドレス・本文内リンク・チーム名をそのままResend経由で送信していた。つまり**NekoMapにログインしていない、任意の第三者が直接このAPIにPOSTするだけで**、「NekoMapからの招待」という体裁のメールを、任意の宛先に、任意のリンク（フィッシングサイト等）付きで送信できる状態だった（メール送信サービスの悪用・なりすまし踏み台）
- 修正: ログイン確認を必須にした上で、クライアントからは招待の`token`のみを受け取り、宛先・チーム名・リンクは必ずDBの実際の招待レコード（`organization_invites`）から取得し直す方式に変更。呼び出したユーザーが実際にその招待と同じチームのメンバーであることも確認する。DBの変更は不要（既存のRLSはこの問題の影響を受けていなかった）
- 併せて`pages/org/index.js`の呼び出し側も、ログインのアクセストークンを付け、`token`のみを送るように変更

### 予防的対策: 基本的なセキュリティヘッダーを追加
- `next.config.js`が存在しなかったため新設。`X-Frame-Options: DENY`（クリックジャッキング対策）・`X-Content-Type-Options: nosniff`（MIMEスニッフィング対策）・`Referrer-Policy`・`Permissions-Policy`（未使用のカメラ・マイクを無効化）を全ページに付与
- 厳格なContent-Security-Policyは、Leaflet・Google AdSense等の既存機能を壊すリスクが高いため今回は追加していない

### 確認したが対応不要・または対応不可だった項目
- Leafletの地図ポップアップのXSS対策（`escapeHtml`）: 全6箇所（目撃情報・野良猫・困りごと・スポット・里親募集・ナワバリ）で正しく適用済みであることを再確認
- サービスロールキー（`SUPABASE_SERVICE_ROLE_KEY`）: サーバー側API（`pages/api/*`）以外では一切使われておらず、クライアントに漏れる経路はないことを確認
- 管理者専用の操作（アカウント種別変更・BAN等）: ブラウザから直接テーブル更新を呼んでいるが、`role`/`account_type`/`verified`は本人には書き換えさせないトリガー（`prevent_self_role_escalation`）で保護されており、管理画面のボタンを隠すだけの見た目の対策に依存していないことを確認
- PostgRESTのフィルタ文字列インジェクション（`.or()`等にユーザー入力を直接埋め込む問題）: 該当箇所はすべてログイン中のuser.id（UUID）を使っており、フリー入力のテキストを埋め込んでいる箇所は見つからなかった
- 画像アップロード（`cat-photos`バケット）のファイル形式制限: クライアント側の`accept="image/*"`だけでは、画像以外のファイルのアップロード自体を強制的に防げない。**これはSupabaseダッシュボード側の設定（対象バケットの「許可するMIMEタイプ」・最大サイズ）で対応する必要があり、コード側では対応できないため、Supabaseダッシュボード → Storage → `cat-photos`バケットの設定確認をお願いしたい**

### 今後の予定（今回は対応していない）
- 「活動者アカウントの公開範囲を広げたい」という話が出た場合は、`lib/blurLocation.js`と`cat_spots`のRLSポリシーの両方に`account_type = 'activist'`を追加する対応が必要（前回の修正履歴を参照）

## 2026-09-30: 「保護団体以上しか見れない情報」と「一般公開情報」の境目を明確化

「切り分けが分かりにくい」との指摘を受け、コード・DBのRLSポリシーを洗い直して実態を確認したところ、現状は以下の2点だけがアカウント種別で制限されていることが分かった（それ以外の一覧・投稿内容はすべて公開）。

- 目撃情報・猫詳細ページの目撃地点の**座標の精度**（`lib/blurLocation.js`・`get_blurred_sightings` RPC）

## 2026-09-28: 新機能「地域（都道府県）フィルタ」の追加

ユーザーからの依頼「現在全国の猫情報が一括で表示されるので地域を絞れるようにしたい。デフォルトの地域を設定しておけばその地域の情報だけ表示されると便利。都道府県や地域別で（ジモティみたいなイメージ）。ピンは全国見れるのが良いが、現在地か設定地域周辺をデフォルト表示だと便利」を受けて追加。

- `trouble_reports`・`adoptions`・`volunteer_requests`・`posts`に任意の`prefecture`列、`users`に`default_prefecture`列を追加（`DB/add_region_filter.sql`）。列追加のみのため既存RLSポリシーの変更は不要
- 困りごと報告・里親募集・ボランティア募集の投稿フォームは、位置確定時に`lib/geocode.js`の`reverseGeocodeToPrefecture`（Nominatim逆geocode）で都道府県を自動判定し、手動修正用の`<select>`も設置。掲示板は位置情報を持たないため手動選択のみ
- 困りごと・里親募集・ボランティア募集・掲示板の4一覧ページに、都道府県または地域ブロックで絞り込める「表示地域」セレクター（`components/RegionSelector.js`）を追加
- 表示地域の判定ロジックを`lib/useRegionFilter.js`に集約。優先順位は (1) その場での一時的な変更 → (2) ログイン中のアカウントのデフォルト地域 → (3) 現在地からの自動判定 → (4) 全国（絞り込みなし）
- `prefecture`が未設定の投稿は、絞り込み条件に関わらず常に表示（位置情報のない投稿を誤って隠さないための意図的な仕様）
- プロフィール編集画面（`/profile/edit`）に「デフォルト地域」設定欄を追加。`users.default_prefecture`に保存
- 地図（`components/MapView.js`）のピンはこの機能の対象外で常に全国表示のまま。地図の初期表示位置のみ、現在地取得に失敗した場合はログイン中のデフォルト地域の中心座標にフォールバックするよう変更（従来は東京固定だった）
- `lib/prefectures.js`を新規追加（47都道府県・8地方区分・都道府県ごとの中心座標のマスタデータ）
- 仕様書・ユーザーマニュアルに本機能の説明を追加（仕様書3.18節、ユーザーマニュアルは6章末尾「地域の絞り込みについて」に集約し、3・7・8・9・17章から参照する形に整理）
